# piece — craft, card, show, yes

1. **Print the piece's rule list, then read each rule in its home.** First write the card's screens and its `Does:` block: one line per screen, `<canvas>.<node> | <trigger>, …`, from `SKILL.md`, "Rule labels" ("always" is never written; it applies everywhere). Then run `venv/bin/python .claude/skills/author-game-lean/scripts/check.py --rules games/<slug> <id>`: it prints every rule that applies, grouped by judge (script, reader, note), each with the craft file that holds it. Read those rows there, and write to them. Why: P13's card named all 16 craft files, 316 rows, and each reader pass covered a different subset (193 to 415 rows); its `Does:` list is 156 rows (LO, relayed 2026-11-24). A card without `Does:` (every card before 2026-11-24) keeps the old way: read the craft file for each area it touches.
   **An area with no craft file comes first.** Before the first piece in that area, write `craft/<area>.md` from the area's section of `lists/COVERAGE.md`, its rows in `lists/LESSONS.md`, and the `later` rows of `lists/CHECKS.md` that touch it. Use the shape of the existing craft files: must-read ids, the shape, an example in roles, "Not this". Show it to LO in bites, take his yes (a CHANGELOG line), and only then card the piece. Why: P06 touched the clock and the shower with no craft file, and the shower became a chore; 1,596 COVERAGE rows are marked port, and economy, phone and returning player had 0 of theirs cited (LO, relayed 2026-11-22: "yes, send item 1 and the pointer fix").
2. **Write** the card at `games/<slug>/cards/<id>.md` from `templates/piece-card.md`. Every slot is filled; "none" is an answer, an empty slot is not. What is not on the card is not built — an author who builds from a card fills its gaps from memory without noticing (C2058). An out-of-scope line scopes out events, never the body of a moment the piece builds (`craft/body-moments.md`, step 7). `Builds:` lists every canvas, place and person id the piece adds or edits, and `sidebar:<trait>` for each sidebar item; `scripts/check.py` turns anything no approved card lists red, as "built but never approved". The `Sheet:` block comes before the prose: one row per screen, its clock in and out, its place, who is there (npc ids, from `who_is_where.py`), what she wears (garment ids) and the flags set before it. `venv/bin/python .claude/skills/author-game-lean/scripts/sheet.py games/<slug> <id>` prints the rows for screens already built; after the build `check.py` compares the two and is red on any difference. A new card has no `Areas:` or `Craft:` line: its `Does:` block (step 1) says what it touches, and `--rules` prints its rules (LO, relayed 2026-11-24: "Yes"). A card from before 2026-11-24 keeps its `Areas:` and `Craft:` lines; on those, `Craft:` names each craft file read and cites every must-read id in it, or skips one with a reason.
3. **Read the card the way the reader will,** before any check. The reader (`reader.md`) judges the built scene against its 13 scene tests (part B) and the truth rule; the writer reads the same, on the card text, first. For each screen, on every path into it and out of it:
   - run part B's 13 tests, and fix the card where one fails;
   - read `craft/voice.md`, "The truth rule", and run its seven steps;
   - for every line that puts a person somewhere, run `venv/bin/python .claude/skills/author-game-lean/scripts/who_is_where.py games/<slug> --person <npc_id>` and check each minute the screen can show.
   Why: P13's reader found new FAILs on all 7 passes, v5 to v11 (99 FAIL rows), with a truth FAIL (test 10 or C460) on 6 of them; the writer had never seen the tests, and `who_is_where.py` ran only in the reader (LO, relayed 2026-11-24).
4. **Check the card** before asking: `venv/bin/python .claude/skills/author-game-lean/scripts/check.py --card games/<slug> <id>`. On a card with `Does:`, it is red when a trigger is not in `SKILL.md`'s Rule labels, when a screen names none or names "always" or "the plan", when `Does:` and `Sheet:` name different screens, or when a card with screens has no `Does:` or no `Sheet:`. On an older card it checks the old `Areas:` and `Craft:` lines (each must-read id cited or skipped with a reason, each named file and area real). Fix red before showing. Paste its verdict line into `Card checks:`. A card with an explicit beat marks each one `[explicit] … [/explicit]` and also runs `check.py --beat games/<slug>/cards/<id>.md`. It is red when a marked beat has fewer than 3 frozen-list words, or when its last sentence has none (`craft/heat.md`). Paste that verdict too. A card cannot leave out what a check needs (C2063). Numbers — word counts, explicit share, ceilings — belong to the checks at build, not to the card (C2069).
5. **Show** the file's own text, exactly, in a code block — no paraphrase. The hash covers the file, so LO sees what gets hashed. A long card goes in bites, one screen at a time, each the file's own text. End with one line of recommendation, then: "Yes, change, or drop?"
6. **Take the answer.**
   - **A plain yes:** `venv/bin/python .claude/skills/author-game-lean/scripts/approve.py games/<slug> <id> "<LO's exact words>"`, mark the piece approved in STATE.md, end with `Next step: build — <id>`.
   - **"Yes, but change X"**, "change …", "keep A, drop B": edit the card, then show only the changed lines, as before and after. LO has seen the rest. The old yes does not carry over; the new yes is recorded against the new file's hash.
   - **Drop:** remove the row from STATE.md; add a NOTES.md line in LO's words.
   - **Silence, "sounds good", an answer about something else:** not a yes. Ask again.
7. **Never build in the reply that shows the card.**
